# Chatwoot provenance

- App: Chatwoot 4.18.0 (`chatwoot/chatwoot:v4.18.0`, MIT core; the `enterprise/` directory has its own licence), deployed on the `neuu` node at `https://neuu.<tailnet>.ts.net:8519`; the unauthenticated `GET /api` reports 4.18.0. Captured 2026-10-06.
- Upstream spec: `swagger/swagger.json` at tag `v4.18.0` (commit `5c1487713ff2ea407188855211533a1e30e24589`), vendored byte for byte as `openapi.json`, sha256 `775d835239f9a0b8270afb03e5700f6435dfac370655fdc811e3230cc34d6ef8`. OpenAPI 3.1.0, `info.version` 1.1.0, 154 operations. It is hand maintained and omits most of the real Rails API, so the entry adds the missing routes (below).
- Cross-check against `config/routes.rb` at the tag (sha256 `1ea1e1db5de4436789d128166fba12a303a2e92313a4113a095f547464cc1638`):
  1. The routes file was expanded with a mock Rails mapper (`resources`, `resource`, `member`, `collection`, `namespace`, `scope`, `only`/`except`/`param`, nested resources; `ChatwootApp.enterprise?` false, `PUT` treated as an alias of `PATCH`). Scope: `api/v1`, `api/v2`, `platform/api/v1`, `public/api/v1`. Result: 480 routes.
  2. 147 of the 154 swagger operations match a route by method and path shape. The other 7: `GET /survey/responses/{uuid}` (a real route outside `api/`, kept), `PUT contacts/{id}` and `PUT /profile` (PUT aliases of the PATCH routes, kept), `reporting_events` at account and conversation level (routes behind `ChatwootApp.enterprise?`, kept), `GET /api/v2/.../reports/conversations/` (swagger path with a trailing slash, kept) and `GET /accounts/{account_id}/conversations/{conversation_id}/messages` (no `/api/v1` prefix: not a real route, **excluded**).
  3. 333 routes are in `routes.rb` but not in the swagger. Each was checked against the controller source at the tag (`app/controllers`, `enterprise/app/controllers`, concerns): the route is kept only when the controller defines the action.
- Added to `overlay.json` (pinned in `entry.json`, sha256 `c4561cbaf47dab1c59314992c697669bfa4c0784e747710ab10c0bba4d58fd00`): **296 operations**, each marked `x-source: code` with `x-code-route` (`VERB /path -> controller#action`), a generated unique `operationId` (such as `captain-assistants-playground`, `v2-reports-agents`), a group tag aligned with the swagger tags, and an open request body (`additionalProperties: true`) plus declared query names for lists. Field and query names are those the controller reads (`params[...]`, `permit(...)`), unioned per controller and unverified per action; replace them when upstream documents the routes. 97 of the 296 live only in `enterprise/app/controllers` (Captain, companies, SLAs, custom roles, capacity policies, SAML settings): they need an Enterprise-enabled install and carry `x-edition: enterprise`.
  - Added by area: Captain 60, conversations 21, integrations 20, help center 20, inboxes 16, companies 14, profile 13, agent capacity policies 11, contacts 11, reports 10, data imports 9, notifications 8, and the rest across macros, notes, assignment policies, dashboard apps, platform and public APIs.
  - Not added (37 of the 333): 7 routes whose controller has no such action (public `inboxes` index, create, update, destroy; account `integrations/hooks` show; `assignment_policies/{id}/inboxes` create and destroy), 23 browser-widget routes (`/api/v1/widget/*`, authenticated by the website token and contact JWT, not an operator API), `auth/saml_login`, `notification_subscriptions` (create, destroy) and `integrations/webhooks` (inbound), 2 PATCH aliases of documented PUT routes, and `GET callbacks/register_facebook_page` (a GET alias of the mutating POST).
  - Behind `ChatwootApp.enterprise?` and not added: 36 routes (billing under `/enterprise/api/v1`, calls, WhatsApp calling, conference tokens, company campaign analytics and similar).
- Operations after the overlay: 450 (154 + 296), 448 exposed, 2 excluded. Exposure: discovery.
- Excluded (2): `getConversationMessages` (not a real route, above) and `get-sso-url-of-a-user` (`GET /platform/api/v1/users/{id}/login` mints a login URL for any user, which a read grant must not do).
- Outward (58, held): message create (a reply to a customer, private notes included), new conversation, status and typing toggles (resolution can send the CSAT survey, typing shows to the customer), transcript email, contact info request, message retry, campaigns, webhooks, integration hooks, Slack, Dyte, Linear, Shopify, automation rules, macro execute, agent bots, inbox create and update, channel and WhatsApp setup, agent invitations, help center portals and articles, contact export, account signup, platform provisioning (accounts, users, account users, agent bots, tokens, email channel migrations) and the public client API's conversation and message create.
- Destructive beyond DELETE (admin): contact merge, `destroy_custom_attributes`, notification destroy-all, access token, secret and HMAC resets, portal archive, platform user token. The 19 swagger DELETEs and the added ones are admin-capability by rule.
- Reads (3): the contact, conversation and contact inbox `filter` POSTs. The Captain `tasks` POSTs (LLM calls that spend credits) are not reads.
- Auth: `api_access_token: <token>`. A user token (Profile settings > Access Token) covers `/api/v1` and `/api/v2` with that user's role; `/platform/api` needs a Platform App token (Super Admin > Platform Apps) and the public client API needs none. The three swagger security schemes all use this one header, so install the token you need.
- Health: `GET /api/v1/profile` (`fetchProfile`), which verifies the user token.
- Reproduction: the route expander, controller check and overlay generator were scratch scripts (Ruby mock mapper, Python for the checks); the overlay file itself is the reviewed artefact.
